# Stage 26 — critical repairs and interface audit

Date: October 15, 2026. Host: macOS 27.0.1 (26A434), Apple Silicon, Xcode 27 / macOS 27 SDK, Swift 6 with complete strict concurrency. Minimum deployment remains macOS 26. Version/build and distribution/signing policy are unchanged. This is a local acceptance candidate, not a published release.

Fixture tests alone are not counted as production recovery. Ad-hoc updates can require native Keychain authorization; the same bundle identifier does not grant the new executable its predecessor's ACL access. The remaining physical-display, fresh-account and update matrix must be completed before publication.

Source and native UI were inspected. Private local evidence is under `.build/stage26-private/` (ignored by Git). ## A. Critical fixes

### Add Files / +

The action path was `ShelfPageView → FilesFeatureModel.addChosenFiles → NativeFileActions.chooseFiles → NSOpenPanel.begin`. The panel had no originating-window/display context, activation, ownership property, or shell interaction lease. Concurrent clicks could create independent tasks. Cancellation passed an empty array to `addToShelf`, falsely displaying a missing-file error. Separately, `RealFileTransferService.subscribe` enumerated Downloads on MainActor to probe access even though Progress subscriptions require no folder read. That could provoke unrelated TCC UI during startup.

`NativeFilePanel` now owns one native panel through completion, configures file/folder and multiple selection, positions from the clicked window's screen (pointer screen only as fallback), requests auxiliary fullscreen/all-app participation, activates/orders the native panel, and holds/releases the existing shell lease. Cancellation and shutdown are balanced; duplicate requests are refused. No Downloads enumeration precedes picker presentation or Progress subscription. Empty selection is a no-op. Shelf continues to hold bookmarks/references; import never moves/deletes originals.

Each mounted Shelf view now owns its own weak anchor and passes its own interaction handler. The former shared-model anchor could be overwritten by the last rendered display, directing another display's action to the wrong window.

### AirDrop / Share

AirDrop deliberately returned no source window, leaving standalone placement to ShareKit. The session also adopted every unrelated key window in the process as potential sharing UI, so closing Settings could incorrectly release a share lease.

ShareKit now receives a small owned native source window positioned on the originating display, with supported auxiliary fullscreen/all-app behavior and a cancel/return control. It avoids the rectangular dimming artifact from using the much larger transparent notch host. The existing single session and shell lease remain authoritative. Terminal callbacks, source-sheet termination, related-window teardown, explicit cancel, and shutdown converge on idempotent cleanup. Only source-related windows are tracked. The source window closes at termination, its observers/delegates are removed, and the same Shelf session is retained. No timer/polling or global activation-policy/level change was added.

A native screenshot established visible AirDrop over the fullscreen browser on the built-in display. Native cancellation and immediate re-entry were exercised. Recipient selection/transmission was deliberately not performed: there was no authorized recipient, and no user file was sent. The public AppKit behavior is a supported placement request, not a universal guarantee across every third-party service, macOS version, or Space configuration.

### Clipboard encryption / Keychain

The shipped service/account has been `Notchium.Clipboard` / `payload-key.v1` since encryption was introduced. Git history showed no alternate service/account to guess. Debug selected Data Protection while the free DMG selected login Keychain; an otherwise identical versioned identity could therefore look missing when switching builds. Both non-Store configurations now select login Keychain for new histories. Store retains Data Protection and its existing entitlement requirements.

Existing encrypted indexes can read the known earlier backend. Its candidate key must authenticate the current AES-GCM index; all referenced images must authenticate before writes, key promotion or migration cleanup become available. A wrong primary key can fall back to the authenticating legacy key without replacing either record. If the canonical non-Store slot is absent, the same fully authenticated original key is added there using create-only insertion and exact readback verification. A concurrent different key fails closed; the legacy record stays intact. Existing ciphertext is not re-keyed. This fixes the gap in read-only fallback: an unentitled DMG cannot itself retrieve a key confined to the earlier entitled backend. Promotion must run through an app legitimately able to access that original key, and subsequent ACL authorization remains macOS-owned.

Fresh creation retains cryptographic randomness, create-once insertion and exact 32-byte readback verification. Existing encrypted files prohibit replacement-key creation. Exact Security failures, missing keys, malformed envelopes, and authentication failures remain distinct. Keychain and disk work stay on the ordered utility queue. Atomic writes, filesystem restrictions, hydration/retry ownership, and capture gating are preserved.

The initial isolated read-only diagnostic returned **-25300 (`errSecItemNotFound`) for both backends** and authenticated no original history. It ran under its own executable identity with interaction suppressed; this did not prove permanent loss. The first installed candidate's ordinary Try Again retained that warning. Later, a running development app showed readable history; a fresh verified backup and executable copy were preserved. The repaired app was then built with the repository's existing Apple Development profile and launched normally. Its exact executable showed original Clipboard rows with no storage, loading or preservation warning. No Clipboard payload was printed. This is legitimate in-app recovery, without library injection, key export, record deletion, ciphertext re-keying or a history reset.

The normal development build succeeded, but a separate strict signature check reported `CSSMERR_TP_NOT_TRUSTED` on this host. macOS allowed the ordinary launch. Certificate trust, entitlements and signing policy were not altered; certificate-chain readiness remains separate from a successful development build.

Automatic approval review rejected a proposed read-only diagnostic loaded into the original signed executable, identifying execution under that identity as a possible Keychain authentication bypass. It was not executed or retried. Legitimate in-app authorization or an original Keychain backup remains the recovery path.

The first verified backup contains 22 Clipboard files plus an encrypted login Keychain database copy. While the older development app was still running, its live encrypted index changed; 21 Clipboard files stayed identical and none disappeared. The initial backup remains verified. A second verified snapshot of all 22 Clipboard files was taken after quitting that app, before acceptance of the candidate. These snapshots are recovery evidence, not a claim that ciphertext can be decrypted without its original key.

A third hash-verified snapshot of 22 Clipboard files and a fresh encrypted login Keychain copy were preserved when the later accessible development session was found. The exact accessible development executable was also copied and hash-verified before testing the repaired build.
